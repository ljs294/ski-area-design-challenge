# Current architecture

This document describes the repository as it is currently landed. Proposed refactors belong in the execution ledger, not here.

## Runtime surfaces

The supported product renderer starts at [`index.html`](../index.html), which loads [`src/app/main.tsx`](../src/app/main.tsx). That entry mounts the React application. [`src/app/App.tsx`](../src/app/App.tsx) owns the top-level screen state for the menu, new-game picker, active game, map management, and graphics lab. It also coordinates save loading, boot progress, settings, and close checkpoints.

[`src/app/MapView.tsx`](../src/app/MapView.tsx) is the gameplay composition root. It owns the committed design collections and document ports, terrain preparation, save/load snapshots, centralized selection, contribution assembly, and capture composition. [`src/app/useMapRuntime.ts`](../src/app/useMapRuntime.ts) owns MapLibre creation, style restoration, camera warm-up, and live render settings; [`src/app/MapViewChrome.tsx`](../src/app/MapViewChrome.tsx) composes presentation overlays, and [`src/app/MapGameDock.tsx`](../src/app/MapGameDock.tsx) composes the feature panels. Every construction workflow is controller-owned. `MapView` remains deliberately within the enforced 1,800-line, 40-import, 15-effect, and zero-worker-construction budgets.

The desktop shell starts at [`electron/main.ts`](../electron/main.ts). It creates the Electron window and registers terrain and game-save filesystem handlers. [`electron/preload.ts`](../electron/preload.ts) exposes a narrow context-bridge API; renderer code consumes it through [`src/desktopBridge.ts`](../src/desktopBridge.ts). The renderer has no direct Node access.

The web build uses [`vite.config.web.ts`](../vite.config.web.ts) and the same React renderer. The existing GitHub Pages workflow builds that static variant.

Two developer surfaces are supported:

- [`src/app/GraphicsLab.tsx`](../src/app/GraphicsLab.tsx) is a React graphics lab opened through `npm run dev:lab` or the application shortcut.
- [`spike.html`](../spike.html) with [`src/spike/spikeMain.ts`](../src/spike/spikeMain.ts) is a standalone MapLibre data-source spike served with the spike Vite configuration.

## Data and persistence

Authoritative models live under [`src/types/`](../src/types/), ordered from dependency-neutral geographic, construction, earthwork, anchor, raw-vector, and snow types through cover and terrain, then lift, road, snowmaking, topology, trail, and finally `GameSave`. The graph is acyclic and model files do not import implementation or application modules. Snowmaking nodes, ski topology, and the persisted snow-grid contract in [`src/types/snow.ts`](../src/types/snow.ts) are defined with their domains; `skiNodes.ts`, `snowmakingNodes.ts`, and `snow.ts` contain behavior only. Root domain modules import authoritative models directly.

[`src/types.ts`](../src/types.ts) is a type-only compatibility facade for aggregate UI and IPC consumers. Its exact named-export manifest, lack of runtime exports, and 100-line budget are enforced by the architecture checker. [`src/gameSaveSchema.ts`](../src/gameSaveSchema.ts) owns the schema version written by new saves; compile-time compatibility tests preserve the `GameSave` field types and optionality while representative schema-v1 and schema-v11 fixtures exercise hydration.

Terrain preparation is orchestrated by [`src/terrainIngest.ts`](../src/terrainIngest.ts). It fetches elevation and surrounding elevation, NAIP data, and vector context; derives four-class cover and display assets; persists and verifies a `TerrainRecord`; and returns that persisted record directly. Browser-only WorldCover sampling enters through the required `ResortPreparationServices` port supplied by `MapView`; preparation progress and cancellation use a named options object. Browser storage fallback and Electron storage are accessed through [`src/terrainStorageClient.ts`](../src/terrainStorageClient.ts).

[`src/app/initialResortDesign.ts`](../src/app/initialResortDesign.ts) is the single load-time sanitizer and cross-entity topology hydration boundary for persisted design collections. [`src/app/useElevationBackfill.ts`](../src/app/useElevationBackfill.ts) isolates the one-time compatibility repair for saves lacking construction elevations, while [`src/app/useMapSampling.ts`](../src/app/useMapSampling.ts) owns picker/local terrain sampling and cursor readout.

`GameSave` currently supports schema versions 1 through 13. Snowmaking pipe segment and pump-port metadata was added at version 12. Version 13 adds the optional compact per-resort snow snapshot; older or malformed snapshots derive a deterministic midwinter baseline without blocking load. Browser storage uses local storage while Electron delegates through the preload bridge to filesystem-backed IPC handlers.

## Map and worker ownership

Map feature ordering is declared once by the contribution registry described below, and every worker is owned by the adapter described below it. [`src/app/toolCoordinator.ts`](../src/app/toolCoordinator.ts) is the synchronous authority for the seven construction tools, dock state, and Layers-alongside-build behavior. Controllers register cancellation callbacks; changing tools cancels the prior owner before publishing the replacement. Selection stays outside that coordinator but enters through one centralized transition in `MapView`.

[`src/app/mapInteractionLease.ts`](../src/app/mapInteractionLease.ts) exclusively leases controller cursor, drag-pan, and double-click-zoom overrides and restores the exact prior map state once on release or disposal. The separate site-box gesture is not a construction controller. Escape remains in each existing feature listener.

## Committed documents

[`src/app/terrainDocument.ts`](../src/app/terrainDocument.ts) is the authority for the committed terrain package. Snapshots expose a recursively read-only record and carry a monotonic revision; a commit names the expected revision, the next `TerrainRecord`, and whether it dirties elevation or cover. A commit built on a superseded revision is rejected with no effect on the record, revision, React state, dirty flags, display caches, protocols, or map sources. One publication moves the height/cover-display/imagery caches, the resort protocols, the React projection with its dirty flag, and only the map sources the change invalidated. Initial load and package preparation use an explicit clean replacement path instead of masquerading as an edit, and `markPersisted` clears the dirty flag only when nothing landed while the write was in flight. `MapView` owns the document, re-binding its ports each render because the contour and source refreshes read the current unit setting; `terrainRecordRef` is a mirror written by the publication, never a second authority.

The same document owns construction ownership and cover-edit serialization. [`src/app/constructionLock.ts`](../src/app/constructionLock.ts) holds `ConstructionActivity` and takes ownership synchronously before a confirmed build reaches its first await, so a second confirmation in the same tick is rejected; release is ticketed, so an older operation cannot hand ownership away from a newer one, and it happens in `finally` on success, failure, and cancellation. Cover edits run one at a time against the snapshot current when each starts, and a cover edit that finishes against a superseded package is dropped rather than published over the newer one — still best effort, and never a rollback of committed infrastructure. `PreviewOwnership` issues the tokens that let a late terrain-grade worker response identify itself as superseded; the existing request-id and geometry/elevation-checksum protections are unchanged.

[`src/app/topologyDocument.ts`](../src/app/topologyDocument.ts) makes trails, ski nodes, connector paths, and junctions one revisioned document. Its owned snapshots are deeply frozen. A transaction takes a working copy, applies pure operations from [`src/topology.ts`](../src/topology.ts), and publishes every collection it moved in one change against the revision it began from; a stale transaction is rejected without partial writes, and identity comparison decides which collections publish, so missing targets and identical patches move nothing and do not advance the revision. Confirming a run materializes both anchor junctions and lands them with the run itself, and deleting a run prunes exactly the junctions nothing references any more, lift terminals excepted. The port owns junction materialization and publication only: `buildSkiNetwork`, coordinate frames, sanitizers, derived-network reads, and feature-controller behavior stay outside it. There is no runtime replacement command because opening another resort remounts the session, so the clean load is the document's construction seed.

[`src/app/committedDocumentTransaction.ts`](../src/app/committedDocumentTransaction.ts) coordinates the one command that changes both documents: confirming a graded trail. Both revisions validate first, both authoritative snapshots apply second, and only then do terrain and topology notify their observers. Save and exit checkpoints read the same synchronous committed topology projection, so React scheduling cannot produce a mixed trail/node/path/junction save.

[`src/app/useLiftController.ts`](../src/app/useLiftController.ts) owns lift draft/review state, sampling identity, leased map input, confirmation/cancellation, and the lift map contribution. Its pure transitions and entity construction live in [`src/app/liftControllerModel.ts`](../src/app/liftControllerModel.ts), while `LiftControl` remains presentation-only. `MapView` retains the committed lift collection behind an add/patch/remove command port and keeps lift selection in the centralized selection transition.

[`src/app/useRoadController.ts`](../src/app/useRoadController.ts) owns road drawing and review state, leased map input, terrain-grade request identity, construction confirmation, cancellation, and the road map contribution. Its pure transitions and saved-road construction live in [`src/app/roadControllerModel.ts`](../src/app/roadControllerModel.ts), while `InfrastructureControl` remains presentation-only. The controller consumes the terrain document and receives committed-road addition, contour preview, and best-effort cover clearing through ports; it does not own the committed road collection.

[`src/app/useSnowmakingController.ts`](../src/app/useSnowmakingController.ts) is the presentation-facing façade over separate dam, standalone-pond, revisioned pipe/node network, and snowgun construction controllers. Dam and pond transitions/entity construction live in their `*ControllerModel.ts` files. The dam controller owns worker-backed analysis and rejects review or confirmation if the terrain revision used for its grade is stale; the pond controller re-solves its earthwork against the live terrain inside the construction lock. The network document publishes pipe, node, label-counter, and snowgun changes atomically; the snowgun controller owns mixed-batch placement and sled relocation while `snowmakingGuns.ts` owns the immutable catalog and deterministic one-to-one hydrant reconciliation. `MapView` retains committed collections behind command ports and centralized selection.

Snowmaking pipes retain one authoritative editable vertex route while persisted segment metadata supplies stable identities and pump-arm roles at every node boundary. New pumps are revision-checked inline placements on one node-bounded segment, with their two opposing ports committed alongside the split; legacy multi-arm pumps retain per-arm editing. `snowmakingNetwork.ts` normalizes that metadata transactionally; `snowmakingRouting.ts` grows a transient, pump-aware radial forest from selected sources to selected guns; `snowmakingHydraulics.ts` solves each retained source tree independently; and `snowmakingHydraulicSolver.ts` contains the dependency-free sparse nonlinear solve. Analysis runs through `snowmakingAnalysis.worker.ts`, with revision ownership, cancellation, and stale-result rejection kept in the application client and hook.

[`src/app/useNodePathController.ts`](../src/app/useNodePathController.ts) owns ski-node and connector-path tool state, leased map input, snapping, cancellation, and the shared node/path contribution. Its pure state transitions and saved-path construction live in [`src/app/nodePathControllerModel.ts`](../src/app/nodePathControllerModel.ts). Committing a path uses one topology transaction to split both trails, materialize the two junctions, and add the connector before publishing; the controller receives committed topology through the document port and does not own sibling collections.

[`src/app/useTrailController.ts`](../src/app/useTrailController.ts) owns trail state, painting orchestration, elevation sampling, grading identity, atomic terrain/topology confirmation, editing, cancellation, and the trail contribution. [`src/app/trailControllerModel.ts`](../src/app/trailControllerModel.ts) contains the pure phase reducer and saved-trail construction, while [`src/app/useTrailMapInput.ts`](../src/app/useTrailMapInput.ts) isolates leased head/tail picking and brush gestures. The controller shares the terrain-grade adapter with roads, consumes the topology and terrain documents through their command ports, and receives cover clearing as a best-effort service after a successful coherent commit. `TrailControl` remains presentation-only.

## Worker adapters

[`src/app/workerAdapter.ts`](../src/app/workerAdapter.ts) runs one worker at a time and binds handlers to the instance that was running when they were bound, so a retired worker cannot deliver into the live tool and terminating is the ordinary way to supersede work. A worker that raises an uncaught error is terminated before its owner is told, because an engine that threw has already lost whatever state the next request would be answered against. Request identity, response validation, and recovery belong to each protocol and stay in the adapter above the session.

`MapView` constructs no workers. [`src/app/useMapWorkers.ts`](../src/app/useMapWorkers.ts) holds one stable adapter per protocol and supplies the shared [`coverClearService.ts`](../src/app/coverClearService.ts); session teardown disposes each adapter. Disposal abandons what is in flight without retiring the adapter, so a StrictMode remount stays usable. [`damAnalysisClient.ts`](../src/app/damAnalysisClient.ts) numbers each alignment and abandons the previous one, so a superseded pond can never reach review. [`terrainGradeClient.ts`](../src/app/terrainGradeClient.ts) is shared by the road and trail tools because one grade preview exists on the map; it checks the preview token, the elevation checksum, and the geometry key before a finished grade is applied, and reports a failure of any of them as superseded. [`trailPaintClient.ts`](../src/app/trailPaintClient.ts) drives the one stateful engine: requests are numbered so an out-of-order preview cannot repaint the canvas backwards, the watermark resets whenever a new engine starts, and one crash is recovered by starting a replacement and asking its owner to replay. [`coverEditClient.ts`](../src/app/coverEditClient.ts) settles one promise per edit — success, refusal, crash, timeout, or teardown — and terminates the worker on every ending.

Worker protocol, engine, and worker entry files live under `src/app/`.

## Map contributions

The required visual order is bottom-to-top: analysis, site boundary, road, dam, pond, ski-node/path, trail, lift, and the combined snowmaking pipe/node/gun contribution. Snow is a terrain-draped raster inside the bottom analysis family and is mutually exclusive with slope and aspect. Its depth/condition presentation is session-only while the compact grid belongs to the resort save, not the shared terrain package. The required hit priority is snowmaking, lift, trail, dam, pond, stream, and lake; within snowmaking, guns pick above nodes and pipes. [`src/app/mapContribution.ts`](../src/app/mapContribution.ts) declares the family orders once and requires every contribution to declare the matching independent rank. An incomplete, repeated, or incorrectly ranked set is refused rather than silently reordered.

`MapContributionRegistry` owns map and style generations plus installation, data synchronization, merged visibility descriptors, hit dispatch, hover targets, capture hide/restore, and reverse cleanup. Every callback receives an explicit generation-stamped map context instead of reaching through a registry-owned map ref. Visibility survives style replacement and one shared Roads descriptor controls imported OSM roads in analysis plus the dedicated player-road source installed by the road family above the site boundary. Every feature controller owns its contribution; `MapView` creates only the cross-cutting analysis and site-boundary families and owns no cross-family traversal. Every hit yields to the layers of the families ahead of it; a run therefore yields to a lift crossing it. Pond paints above dam while dam picks ahead of pond: that inversion is deliberate, since a dam's crest is the structure a click is aimed at and the pool it impounds is not.

## Verification state

Vitest tests are colocated with source as `*.test.ts` and `*.test.tsx`. `npm test` and `npm run test:unit` are deterministic offline gates; live-provider cases use `*.integration.test.ts` and run only through `npm run test:integration:live`. Playwright Test uses a managed fixed-port preview, deterministic save/terrain fixtures, blocked external HTTP, one worker, and failure-only traces/screenshots. `npm run check:e2e-harness` proves nonzero failure propagation; `npm run test:e2e` runs the deterministic browser smoke and feature projects. The opt-in live-provider project performs a real New Game preparation and verifies provider traffic plus the persisted schema-6 package; the opt-in Electron project launches the packaged executable and verifies the main menu. The older `scripts/verify*.mjs` files are not gates.

TypeScript runs with `strict` plus the existing unused-code and switch checks. Flat ESLint configuration enforces the React rules of hooks and treats unexplained or obsolete suppressions as errors. [`scripts/checkArchitecture.mjs`](../scripts/checkArchitecture.mjs) checks core-to-app boundaries and type-model isolation/cycles; there are no core-to-app exceptions.

`npm run check` is the canonical deterministic gate: agent-document checks, architecture checks, lint, strict typechecking, offline unit tests, desktop and web production builds, and an obsolete-vertical guard over source paths, package metadata, and built output. [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs `npm ci`, that aggregate command, the negative-control harness proof, and deterministic Playwright workflows for pull requests and protected development branches. Repository branch settings must make the workflow required; the workflow file cannot enforce that setting by itself.
